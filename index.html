SASA Intelligence Lab · Data issues · 2 September 2026

What I found
in the data.

I have been building an analytics prototype on the SASA datasets in the Data Lake. This is a list of everything that got in the way, grouped by who is most likely to fix it rather than by how serious it is, so each team can find their own part quickly.

What would help

Three things, and none of them are large. First, a view on the three items in “Priorities” below, particularly what a zero means, because that one decides whether the new daily datasets can be used at all. Second, confirmation on the ULB code question in A3, which is worth settling before it is built into every dataset. Third, a date for the five CDMA datasets and three PR datasets that are documented but not yet on the portal.

Everything here can be reproduced. The section near the end gives the exact requests, so nothing needs to be taken on trust. I re-ran every check in this document against the live API on 2 September before sending it, rather than relying on my earlier notes. Three earlier claims did not survive that and are listed at the end rather than removed. Happy to walk through any of it on a call if that is easier than reading.

Section A · The data

Issues in the data itself

These are about the data itself, what is in the files and how it is named and coded. Some are fixable in processing. The ones about what was never recorded in the first place are not, and those are marked as the department’s.

A1

The same town has different names in different datasets

Dept or TCS
Checked live

ULBs are identified by name, and the spelling changes from file to file. So the data for one town sits in files that cannot be joined together.

Re-checked live on 2 September across 29 datasets.
263 different ULB name strings. After ignoring capitalisation, 195.
68 groups differ only by capitalisation. 14 differ in actual spelling.

Atmakur has 10 spellings: Atmakur, Atmakur K, Atmakur N, Atmakur (K), Atmakur (N), Atmakur(N), Atmakur (KNL), Atmakur (NLR), ATMAKUR-N, ATMAKUR-KURNOOL.
Gudur has 10: Gudur (K), Gudur (N), Gudur(K), Gudur(N), Gudur N, Gudur (KNL), Gudur (NLR), Gudur Tpt, Guduru (K), GUDUR_KURNOOL.

Two ULB names come back with literal double-quote characters inside the value: "JANGAREDDY GUDEM" and "YSR TADIGADAPA". That looks like a CSV escaping problem that has been carried through into the API.

Others that differ by more than punctuation: Adanki and Addanki, Akiveedu and Akivedu, Mumidivaram and Mummidivaram, Gollaprollu and Gollaprolu, Yellamanchalli and Yelamanchali.
What would fix this: a permanent ULB ID on every dataset, old and new.
A2

district_id already exists but it is not reliable

TCS
Checked live

Eleven datasets have a district_id. It cannot be used as a key. This is worse than having no ID at all, because anyone who sees a field called district_id will assume it is safe to join on.

Re-checked live on 2 September across the 11 datasets that carry it. 56 distinct values.
15 of the 56 point to more than one district name. 10 of those are genuinely different districts, not spellings of one:
id 17 is Bapatla and Kakinada. id 22 is NTR and Palnadu. id 23 is Palnadu and Tirupati.
id 26 is Tirupati and Nandyal. id 27 is Polavaram and Markapuram.

The other 5 are one district spelled several ways, for example id 9 is SPSR Nellore, S.P.S Nellore and Sri Potti Sriramulu Nellore.

Separately there are 67 different district spellings for the 28 real districts. Andhra Pradesh moved from 26 districts to 28 on 31 December 2025, when Markapuram was carved out of Prakasam and Polavaram out of Alluri Sitharama Raju. Both appear in the retained data, so the sources are current on this. An earlier version of this note said 26, which was my error, not the data's.
What would fix this: either make district_id stable, or drop it and use the LGD district code.
A3

ulb_code has the mandal code in it, not a ULB code

TCS
Checked live

A mandal and a ULB are two different things in LGD, with their own separate codes. They look the same in the sample only because Guntakal happens to be both a mandal and a municipality with the same name.

Re-checked live on 2 September across 500 rows of the door to door dataset.
487 of 500 rows have ulb_code exactly equal to api_lgd_mandal_code. It is the mandal code.
Example: ulb_name: "GUNTAKAL", ulb_code: "1003", api_mandal_name: "GUNTAKAL", api_lgd_mandal_code: "1003".

The 13 rows where they differ are the proof. ulb_name: "VISAKHAPATNAM(GVMC)" has ulb_code: "1086" but api_lgd_mandal_code: "1089", which is GVMC (Bheemili). GVMC covers more than one mandal, so a mandal code cannot identify it.

There is no LGD urban local body code column anywhere in any of the 33 datasets.
Worth settling early. As I understand it, this is being added to every dataset now, so it is much cheaper to correct before that than after. The LGD urban local body code would work; the mandal code will not.
A4

There is no way to tell a real zero from "not reported"

Dept
Checked live

There are four different ways a missing value shows up, and none of them can be told apart from a genuine zero.

In the older datasets there is 0, empty string "", null, and the field simply not there.
Across 123 entities and 18 sources, 1,063 of 2,214 possible values (48%) never came back at all.

Now worse in the live CDMA data. Sampled across the whole 64,368-row file on 2 September, 93% of rows show collected_households: 0 and not one row is blank or null. In the older datasets a non-report at least looked different from a zero. Here every non-report is coming through as a zero, so there is no way at all to tell the two apart. See A13.
What would fix this: one clear code for "not reported". This becomes critical with the new daily data. collected_households: 0 against total_households: 886 could mean collection failed, or it was a holiday, or nobody submitted that day. There is no way to work out a collection percentage without knowing which.
A5

Month number and month name do not match

Dept or TCS
Checked live

Inside the same row, the two period fields disagree. On every row of a whole dataset.

Re-checked live on 2 September across 374 rows that carry both fields.
35 of them have month_number = 7 with month_name = JUNE. All 35 are in the FSTP dataset, every July row of it.

Two more period problems found in the same pass:
Trailing spaces. In the SERP datasets the month value is "July" on 25 rows and "July " with a trailing space on 3. Those will not group together.
Inconsistent case. The same month is "July" in the SERP datasets, "july" in the door to door ones and "JULY" in the legacy waste one.

There are four different names for the month filter across the 33 datasets: mnth_no on 12, month_number on 7, month on 5, month_id on 3.
What would fix this: one standard period field, and the values inside a row should agree with each other.
A6

There is no way to tell if a number is monthly or cumulative

Dept
Checked live

Similar datasets mix the two with nothing to say which is which, so a correct number looks like a mistake.

SERP circular economy shows 11,084 against a target of 5,000, which is 221%.
The reason: the field is cummulative_achievement_till_current_month while similar datasets are monthly.
What would fix this: say whether each measure is monthly or cumulative, and give the denominator for every percentage field.

A8

No record ID, submission date or revision number

TCS
Checked live

There is no way to point to a specific record, know when it was submitted, or tell that it has changed since it was last read.

Re-checked live on 2 September against every readable dataset.
0 of 32 have a record ID. 0 of 32 have a submission or created date. 0 of 32 have a revision or version number.

This is what makes the duplicate rows in A14 impossible to resolve. When the same place and month comes back twice with different numbers, there is nothing on either row that says which one is current.
What would fix this: record ID, submission date and revision number on every row. This was on the list I shared earlier and has not been done yet.

A13

In the new daily data, most collection values are zero and none are blank

Dept
Checked live

This is the most important thing I found today, and it decides whether the new datasets can be used at all.

Re-sampled properly on 2 September. 23 sample points spread evenly across the whole file, 2,300 rows, covering all 64,368.

2,144 of 2,300 are zero. That is 93%.
0 are blank. 0 are null.

11 of the 23 sample points are 100 of 100 zero, including YSR Kadapa, East Godavari, Visakhapatnam, West Godavari, Konaseema, Palnadu, Sri Sathya Sai, Nandyal and Markapuram.
Only one sample point is mostly non-zero: Anantapuram, at 28 zero out of 100.

The denominator is fine, the numerator is not. total_households is filled in on every row, with only 3 zeros in 2,300. It is collected_households that is zero 93% of the time.

An earlier note of mine put this at 79% from a single slice of the file. Sampled across the whole thing it is worse.
What cannot be told apart: whether collection genuinely is not happening in those districts, which would be a serious finding, or whether it simply is not being reported. Because there is not one blank value anywhere in the file, the two look identical. Until this is answered I cannot publish a collection percentage from this data.
A14

The same place and month comes back twice, with different numbers

Dept or TCS
Checked live

Found on 2 September while re-checking everything else. This is the one I would look at first, ahead of anything in this list except the zero question.

8 of the 29 monthly datasets contain more than one row for the same place in the same month. Sometimes the copies are identical, which is untidy but harmless once you spot it. Sometimes they carry different numbers, and then there is no way to tell which is the real one.

ODF Plus model villages. 84 rows. Every one of the 28 districts appears twice for MAY. 18 of those pairs are identical. 10 contradict each other:

ALLURI SITHARAMA RAJU, MAY: achievement 1296 (97.96%) or 389 (29.4%)
ANAKAPALLI, MAY: achievement 180 (59.6%) or 301 (99.67%)
CHITTOOR, MAY: achievement 0 (0%) or 18 (38.3%)

Sweeping machines. 28 rows, 2 duplicate pairs, both contradictory. Nellore in June and again in July: no_of_machines_supplied is 19 on one row and 4 on the other.

Identical copies, less urgent: IHHL 6 pairs, legacy waste 3, greencover 1, e-autos service model 1.
What would fix this: for the contradictory ones, someone needs to say which row is right. Going forward this is A8: with a record ID and a revision number the newer row wins and the question answers itself. Without them, a reader has to guess, and a dashboard will silently pick whichever row it happened to read last.
Section B · The API

Issues with the platform

These have nothing to do with the data. They affect anyone building on the API, and most of them only show up once you start pulling data properly.

B1

Filtering by month gives a different answer than reading the whole dataset

TCS
Checked live

I had this one written up as a wrong record count. When I re-tested it properly on 2 September the count itself was fine, so I have rewritten it. The underlying problem is real and it is worse than a bad count: the same dataset gives two different answers depending on how you ask for it.

IHHL, every page pulled and counted, 2 September.

Read the whole dataset: 246 rows, and totalRecordCount says 246. Correct.
Count the months inside it: June 127, July 119.

Now filter instead.
Filter to July: 123 rows, count says 123. Filter to June: 123 rows, count says 123.

Both add up to 246, but they disagree about which month the rows belong to.

Six ULBs come back as JUNE when you read the whole dataset and as JULY when you filter to July. Kurnool, Yemmiganur, Naidupet, Sullurpeta and Tirupati among them. Same district, same ULB, same figures, different month.

It is not a fluke. I pulled the whole dataset twice and got byte-identical results both times.

Reading the whole dataset covers all 123 ULBs. Each filtered read covers only 121.
Why this matters: the two normal ways to get a month of data disagree, and neither announces it. A monthly figure built by filtering will not match the same figure built by reading the dataset and grouping. There is no way from the outside to tell which is right.
B2

The filter names in the docs are wrong, and a wrong name gives a 502

TCS
Checked live
GET /api/v1/datasets says legacy waste takes dstrt_nm, mnth_no and year.
All three give HTTP 502. The one that actually works is month_id with year.
A wrong filter name gives a 502 with no list of valid names, so there is no way to find the right one.
What would fix this: correct the published filter names, and return a 400 with the accepted filters instead of a 502.
B3

Gobardhan is the only dataset of the 33 that cannot be read at all

NextGen or TCS
Checked live

I saw the message in the group saying Gobardhan data had been uploaded, so I went back and checked it again on 2 September. Whatever was loaded, it still cannot be read through the API. I had been treating this as a dataset I did not have access to. It is not an access problem, it is a broken table, which is probably the quicker thing to fix.

Checked all 33 datasets with the same token and the same request shape.
32 returned 200. Gobardhan is the only one that fails.

Every route fails with 502 internal_error:
query with no filter, query with year and mnth_no, query with dstrt_id, and /export.

Authorisation is not the problem. Asking with purpose: AUDIT returns a clean 403 naming the allowed purpose, so the access layer knows the table and permits it. Asking with the allowed BENEFIT_DISBURSEMENT is what returns the 502, so the failure is behind the access check, not at it.
What would fix this: raise it as a bug on sasa_establishment_of_gobardhan_units_api rather than as an access request. If the upload has already happened, then the load worked and the serving side did not, so it is worth checking whether the table was created but never registered or indexed.
B4

Page size is stuck at 100 and the token expires in 300 seconds

NextGen or TCS
Checked live

There is no way to ask for a bigger page. And the token runs out well before a large pull finishes, so it has to be refreshed halfway through.

Re-checked live on 2 September.
pageSize is ignored, not rejected. I asked for pageSize: 2 and got returnedRecordCount: 100 back, with no warning.
The token lifetime is exactly 300 seconds, read straight off the JWT (exp minus iat).
My own sweep today hit a 401 part way through a pull and had to re-authenticate and resume.

The CDMA datasets are about 64,000 rows each, so around 644 calls each and 1,900 for the three.
The PR door-to-door one is 1,241,643 rows, which is about 12,400 calls.
What would fix this: either a settable page size, or a bulk export option. This needs sorting before the 26 extra KPIs arrive.
B5

Allowed purposes are different per dataset but not published

NextGen or TCS
Checked live
Asking for Gobardhan with purpose: AUDIT gives:
"Purpose 'AUDIT' is not allowed for tableKey ... Allowed: BENEFIT_DISBURSEMENT"
Nothing in the catalogue says which purposes each dataset accepts.
What would fix this: show the allowed purposes for each dataset in GET /api/v1/datasets.
B6

No way to check whether a dataset changed

NextGen or TCS
Checked live

To find out if anything changed, the whole dataset has to be downloaded again. Together with A8, there is no change signal at all.

What would fix this: a content hash per dataset per month. It is a small change and it lets anyone check for changes without pulling everything again.
B7

The same filter has a different name on different datasets

TCS
Checked live

This one is now measurable rather than a documentation observation. I read the filter list off all 33 datasets in the catalogue.

District has three names: dstrt_id on 4 datasets, district_id on 3, dstrt_nm on 1. The other 25 offer no district filter at all.

Month has four names: mnth_no on 12, month_number on 7, month on 5, month_id on 3.

Only year is consistent, on 27 of the 33.

So anything that reads across datasets needs a lookup table of filter names per dataset before it can ask a single question.
What would fix this: one name per concept across all datasets. district, month, year.

Section C · Decisions

Things that need to be agreed together

These are not one team's job. They are conventions, and once they are set everything else follows.

C1

Agree on LGD codes, and on which LGD code

All three
Checked live

LGD is the national standard and it is already partly in the data, so this is mostly tidying up rather than new work. The question is which code, and A3 shows the data is currently heading for the wrong one.

What is needed is lgd_district_code and a proper LGD urban local body code.
There are already two different conventions in one section: api_lgd_dist_code in 15.1 to 15.5, and lgd_district_name (empty) in 15.6 to 15.8.
Also to agree: will the new columns be added to old rows too, or only new data? And will the old columns be removed? A row already has both district_name and api_district_name. Adding a third without removing the others makes it harder, not easier.
C2

Agree what a zero means, before the daily data arrives

Dept
Checked live

This is the one answer that decides whether the new CDMA data is usable. At monthly level the ambiguity was survivable. At daily level there is no way to work out a collection percentage without it.

From the live data on 2 September, sampled at 23 points across all 64,368 rows: 93% show zero collection and not one is blank. 11 of the 23 sample points are zero on every row. So a day where nobody collected and a day where nobody submitted look identical in the file.
Decision needed: one code for "not reported", different from a real zero, used the same way everywhere.
C3

Check the data before it is accepted

Dept or TCS
Suggestion

Many of the items in Section A are the kind of thing an automated check at submission would catch, including the misspelled table key and the duplicated sample in A12.

Suggestion: validate against the schema at ingestion and send the errors back to whoever submitted, instead of it being found downstream.

What I corrected before sending this

I re-ran every check in this document against the live API on 2 September rather than trusting my earlier notes. Most held up and several turned out to be worse than I had written. Three did not survive, and they are recorded here rather than quietly deleted.

Rows are not being re-dated over time

In an earlier note I suggested records were being moved between months without a marker. Tested properly, that is not happening: the export today is identical to the copy taken on 28 August and all 29 datasets match. What is true is narrower and is written up as B1. At a single moment in time, reading a dataset whole and reading it through a month filter give different months for six ULBs. That is a read problem, not rows being edited underneath us.

The record count is not wrong

I had B1 written up as totalRecordCount returning a fixed entity count on filtered requests. Re-tested on 2 September, the count matches the rows returned in every case I tried, filtered and unfiltered. B1 has been rewritten around what is actually wrong.

I also wrote that the state has 26 districts. It has had 28 since 31 December 2025, when Markapuram and Polavaram were created. Both are present in the data, so the sources were right and I was out of date. Corrected in A2.
